# Saudia AEM packages

## Content Fragment Models + fragments — `dist/saudiaeds-cf-models-1.6.0.zip`

Generated by `python3 tools/aem-packages/build-cf-models.py` (source tree in
`saudiaeds-cf-models/`; booking engine content in `booking-engine-fragments.json`, extracted
from the migrated pages; the home page stories in `story-fragments.json`). Install on the AEM
author with **Tools › Deployment › Packages › Upload Package › Install** (an administrator, or a
user with write access to `/conf/saudiaeds` and `/content/dam/saudiaeds`).

Models are stored under `/conf/saudiaeds` (AEM keeps Content Fragment Models in a
configuration, never in the DAM); the package links the DAM folder `/content/dam/saudiaeds` to
that configuration, which is what makes the models available there.

### Models (`/conf/saudiaeds/settings/dam/cfm/models/…`)

| Model | Fields |
|---|---|
| `booking-engine` — Booking Engine | title*, tabs* (multiple), tripTypes* (multiple), milesLabel, fromLabel*, defaultOrigin, toLabel*, swapLabel, infoMessage, infoLink → Booking Link, links → Booking Link (multiple) |
| `booking-link` — Booking Link | label*, url*, external (opens a new tab, shows the external-link icon) |
| `destination` — Destination | name*, heading, heroImage, heroImageMobile, heroImageAlt, intro, itinerary, faqs → FAQ Item (multiple) |
| `faq-item` — FAQ Item | question*, answer* |
| `story` — Story | title*, summary (multi-line text, HTML), image and imageMobile (image or SVG document), imageAlt, pressRelease → page, link, linkText (defaults to "Learn more") |

`*` required. Image fields reference assets under `/content/dam/saudiaeds`; page fields
reference pages under `/content/saudiaeds`; rich-text fields store HTML.

Story fragments feed the stories block (see *Connecting the stories block* below); authors
create them in `/content/dam/saudiaeds/fragments/stories`.

### Content Fragments (`/content/dam/saudiaeds/fragments/…`)

- `booking-engine/<page>` — one Booking Engine per page that shows the booking engine:
  `home` (5 tabs, 3 trip types incl. Multi-city, 4 quick links: Stopover, Flight + Hotel, Umrah,
  Hotels) and the nine destinations `abha`, `antalya`, `athens`, `bodrum`, `el-alamein`,
  `malaga`, `mykonos`, `nice`, `salalah` (their tabs, trip types and Flight + Hotel promo link —
  Abha and Mykonos have none).
- `booking-links/<name>` — the 12 links those fragments reference (`travel-requirements` is
  the shared notice link; promo and quick links are named after their page, e.g.
  `athens-book-flight-hotel-30-off`, `home-stopover`).

The destination pages' captured tabs listed "Flight status" twice; the fragments list it once.

- `stories/<name>` — the three home page stories, each pointing at its press release:
  `thaqafeyah-in-flight-entertainment` (press-release-05052025-3),
  `skytrax-2025-best-airline-staff-service` (press-release-17062025) and
  `skytrax-2026-top-15-airlines` (press-release-18092026): title, summary, press release, link
  text "Learn more". Their images are left empty, so the stories block shows each press
  release's own image; pick an image in a fragment to override it.

The `stories/` folder is installed with filter mode `merge`: the packaged stories are created
once, and re-installing never changes or removes Story fragments already there (authors' edits
and their own stories survive).

### What else it changes

It sets `cq:conf=/conf/saudiaeds` on `/content/dam/saudiaeds/jcr:content` (merged, no other DAM
content is touched), so the models are offered under **Create › Content Fragment** in that
folder. The filter covers only the five model nodes, that property node, the two booking
fragment folders (re-installing restores those to the packaged state), the stories folder
(merged), the `saudiaeds` GraphQL endpoint node and the two persisted query nodes
(re-installing restores the packaged query text); it touches nothing else.

### How the blocks load fragments

The booking and stories blocks follow the content-fragment conventions of
[waringme/eds-reusable-blocks](https://github.com/waringme/eds-reusable-blocks/tree/main/blocks/content-fragment):

- **Settings** in `window.edsReusableBlocks.contentFragment` (set in `scripts/scripts.js`):
  `publishHost` (`https://publish-p208666-e2180259.adobeaemcloud.com`), `queryNamespace`
  (`saudiaeds`), `siteRoot` (`/content/saudiaeds`, removed from page links on the site) and
  `connection` (`aemconnection`, the Universal Editor connection). Page metadata
  `aem-publish-host` / `aem-query-namespace` is used only when a setting is missing.
- **Author** = an `author-*.adobeaemcloud.com` host (override with `author: true|false`): queries
  go to the current origin with same-origin credentials, and the editor annotations
  (`data-aue-resource` `urn:aemconnection:<fragment>/jcr:content/data/<variation>`, type
  `reference`, filter `cf`; fields as `data-aue-prop`) are added there only. The site queries
  publish without credentials.
- **Requests**: `/graphql/execute.json/saudiaeds/<query>;path=<path with its slashes>;variation=<v>;ts=<t>`
  (AEM does not decode `%2F`); `ts` changes every 5 minutes for visitors and on every author
  request. Variations are lower case with underscores; empty means `master`. Only
  `/content/dam/…` paths are loaded.
- **References**: images as `ImageRef` or `DocumentRef` (SVG), shown from their publish URL (author
  URL on author); pages as `PageRef`, linked without the site root on the site and as
  `<path>.html` on author. Rich text (`{ html }`) is sanitised before it is shown.
- **Failures** are logged (`console.error`). The booking block follows the reference strictly: no
  fragment picked shows a picker prompt, and a fragment that can't be loaded shows "Could not load
  booking engine fragment …" to everyone (with the reason on author). The stories block keeps
  its fallback for visitors (the press release, then the story's own fields) and shows the
  message on author only.
- The site must be allowed to call publish (CORS, see the setup below) and, if the site sets a
  Content-Security-Policy, its `connect-src` and `img-src` must include the publish origin.

### Connecting the stories block (stories → Story fragments)

Each story of a stories block has a **Story content fragment** picker (`fragment` field, opens
`/content/dam/saudiaeds/fragments/stories`). With a fragment picked, the story shows the
fragment's title, summary, images, alt text and link text, loaded through the persisted query
`saudiaeds/story-by-path` (`graphql/story-by-path.graphql`), the same way as the booking engine
(author inside Universal Editor, publish on the site). What the fragment leaves empty comes from
the press release it references, and the story links to that press release, else to the
fragment's own Link. In Universal Editor the story is a reference to the fragment: its title,
summary and image are edited in place.

Without a fragment (or when the query can't be reached) the story uses its own Press release
field, then its own image and text fields, so nothing changes on the site before the setup is
done. The setup is the booking one below; step 4 persists `story-by-path` as well (the script
persists every query in `graphql/`), and step 5 also covers the Story model, the stories folder
and the fragments in it.

The query reads the press release reference as `... on PageRef { _path }`. Check it persists on
the author; if AEM rejects the `PageRef` type there, the press release field can't be read
through GraphQL and stories should use their own Link instead.

### Connecting the booking block (pages → fragments)

Every booking block (home + nine destinations, and the en-sa Athens page) carries a required
**Booking engine content fragment** reference (`fragment` field, e.g.
`/content/dam/saudiaeds/fragments/booking-engine/home`); it is the widget's only source. The
block loads it through the GraphQL persisted query `saudiaeds/booking-engine-by-path`
(`graphql/booking-engine-by-path.graphql`) — from the author inside Universal Editor, from
publish on the site — and renders the widget from it. The earlier authored label fields (tabs,
trip, route, info) are no longer in the block model and are not shown.

**Until the setup below is done, every booking block shows "Could not load booking engine
fragment …" instead of the widget** (and the browser console logs the error): install the
package and replicate it (models, fragments, endpoint, queries — steps below).

One-time setup on AEM:

1. **Configuration Browser › saudiaeds › Properties**: tick *Content Fragment Models* and
   *GraphQL Persisted Queries* (a package can create the folders but not tick these on an
   existing configuration).
2. **Install** this package. Since 1.6.0 it also creates the GraphQL endpoint
   (`/content/cq:graphql/saudiaeds/endpoint`) and both persisted queries
   (`/conf/saudiaeds/settings/graphql/persistentQueries/{booking-engine-by-path,story-by-path}`,
   the text of `graphql/*.graphql`), as the admiral-xwalk content fragment package does.
3. **Publish everything in it at once**: Package Manager › the package › **More › Replicate**
   (models, fragments, endpoint and queries). Without this step publish answers the site with
   `PersistenceError: Could not find Persisted Query`.
4. **Check** what the site sees: `tools/aem-packages/persist-queries.sh` with your own
   credentials (`AEM_TOKEN=<access token> …`; it re-saves the queries from `graphql/`, `PUBLISH=1`
   publishes them too, and it ends by calling both on publish the way the site does — non-zero
   exit until they answer with data and a CORS header). Use it again after changing a query.
5. CORS: the site (`*.aem.page`, `*.aem.live`, the production domain) must be allowed to call
   `https://publish-p208666-e2180259.adobeaemcloud.com/graphql/execute.json/*`. Checked on
   2026-11-04: publish already answers the preview origin with `Access-Control-Allow-Origin`;
   check the live and production origins the same way (`ORIGIN=… persist-queries.sh`, or
   `curl -H "Origin: <origin>" -I "<publish>/graphql/execute.json/saudiaeds/booking-engine-by-path;path=/content/dam/saudiaeds/fragments/booking-engine/home"`).

**Troubleshooting** — the blocks report AEM's GraphQL error (on author in the message, on the
site in the console):

- `PersistenceError: Could not find Persisted Query` — the query is not on publish: install
  package 1.6.0 or later and replicate it (steps 2–3), or persist and publish it with the script
  (step 4). This was the state on 2026-11-04 for both queries.
- `… does not resolve to an existing Persisted Query` with another configuration name — the
  `queryNamespace` setting (scripts.js) and the configuration the query is saved in differ.
- a GraphQL validation error when persisting — the models on AEM differ from this package
  (re-install it); the queries are validated against the packaged models' schema before release.
- no `Access-Control-Allow-Origin` — step 6.

Then edit a fragment (e.g. rename a tab in `booking-engine/home`), publish it, and the home
page's booking engine shows the change — no page edit needed. In Universal Editor, select the
booking engine to open its fragment; its single-value labels and the link labels are editable
in place.

### Check after installing

1. **Tools › General › Content Fragment Models › saudiaeds** — the five models listed as
   *Enabled*. If the `saudiaeds` configuration does not offer Content Fragment Models, enable it
   once in **Tools › General › Configuration Browser › saudiaeds › Properties** and re-install.
2. **Assets › Files › saudiaeds › fragments › booking-engine** — open `home`: Tabs shows 5
   entries, Promo and quick links shows 4 Booking Link fragments.
